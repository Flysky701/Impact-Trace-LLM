# 项目定位

状态：已有本机 Web 骨架，支持双角色登录、项目访问、Git 历史与源码浏览；核心影响分析与模型报告尚未实现。更新时间：2026-10-02。

2026-11-06 补充：[项目现状](project-status.md)按源码区分正式能力与演示原型；[阶段计划](roadmap.md)替代旧日历排期。既有课程约束保持不变，后续扩展按[功能规划](requirements.md#功能扩展规划)逐项选择。

本轮产品方向：面向团队的 Git 代码审阅工作台，以前后流程对照、旧图标红、分层架构和源码证据为主，测试指标与问答为辅。首批仍以 Python/TinyDB 实现；公司私有仓库、认证及部署属于后续接入条件。页面与范围以[产品设计 v0.3](product-design.md)为准。

## 主题与目标

项目名称：基于 LLM 与代码知识图谱的软件变更影响平台。

项目来自课程作业。发起者在使用 AI 辅助编程时，对项目整体架构理解不足，也难以预测 AI 修改代码后的影响。希望平台帮助自己建立项目的基础理解，了解 AI 修改代码的过程，并增加代码与变更的可解释性。

因此首版需要回答：项目由什么组成、主要部分如何关联、一次 AI 任务实际修改了什么、哪些地方可能受到影响以及依据是什么。

## 已确认约束

- 用途：课程项目，以可演示和功能基本可用为交付目标。
- 时间：一个月以内；暂按四周安排，课程的确切截止日期待补充。
- 开发人数：实际由 1 人开发，排期按单人工作量安排；旧对话中的 2 人信息不作为当前实施依据。
- 样例：采用 TinyDB，已核对 744 个可达提交与两个历史修复案例，见[样例验证](sample-validation.md)。
- 语言：首版分析 Python，采用 ast 加有限符号解析；保留多语言接口，第二语言作为扩展。
- 课程要求：8～10 个核心功能、至少两类用户角色、Web 系统、测试覆盖率 ≥75%；课程没有更细规定，项目采用前后端自有业务源码行覆盖率分别 ≥75%，见[测试方案](testing-plan.md)。
- 系统角色：开发者负责项目、仓库和分析任务；审核者／测试负责人负责风险确认、审核意见和测试结果记录；两者均可查看图谱与报告。
- 首版范围：保留基础项目结构浏览和 AI 修改任务记录，优先完成变更分析与审核流程，再补齐这两项能力。
- 模型：候选为 DeepSeek 或 OpenAI，用户提出 OpenAI 使用 OAuth 授权；DeepSeek 按官方 API Key 方式评估，OpenAI 按官方 Sign in with ChatGPT 的订阅用量授权方案评估。仅发送公开开源样例的相关源码片段；具体模型、账号资格、实际调用能力及预算待验证或补充。
- 技术与部署：用户没有明显技术偏好，由助手提出方案；先按本机启动、浏览器演示设计，最终是否需要服务器部署待定。

## 拟解决的问题

- 代码依赖分散在文件与模块中，人工追踪调用方和间接依赖需要时间。
- 单看代码差异难以解释变更在业务语义上的影响。
- 影响分析结果需要可核对的证据，便于评审与回归测试安排。

上述问题来自发起者的实际诉求，具体功能优先级通过选定的演示案例进一步收敛。

## 建议的首版边界

- 首版分析单个 Python 仓库的两个提交，保留统一解析接口；第二种语言作为核心流程稳定后的加分项。
- 支持单版本项目结构浏览与说明，不要求先有变更才能使用。
- 先支持两个明确提交之间的离线分析。
- AI 修改过程先通过用户任务描述、可选的外部操作记录和前后提交关联展示。没有记录的过程标注缺失，不声称从 diff 还原模型内部思考。
- 先建立可解释的静态分析结果，再验证加入 LLM 的收益。
- 报告表达“潜在影响”，保留解析失败、未解析依赖及模型不可用等状态。
- 首版实现登录、两个角色的必要权限和审核状态。成员邀请、自定义角色、平台内自动编写与执行代码、自动运行被分析仓库的测试、跨语言调用链、跨仓库分析和自动合并作为后续范围。

## 成功的判断方式

以一个具备一定 Git 历史的小型开源仓库和少量变更案例完成课程演示：能够说明项目主要结构，展示一次 AI 修改的任务与实际改动，定位潜在影响并打开对应源码；开发者发起分析后，审核者能确认风险并记录测试结果。自动化测试覆盖率须达到 ≥75%，记录统计口径、已知局限和失败处理结果。大规模准确率评测、压力测试及生产级可靠性建设不作为当前交付前提。
