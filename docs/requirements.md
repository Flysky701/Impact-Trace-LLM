# 需求分析草案

状态：建议范围，尚未评审通过。本文不代表功能已经实现。

## 核心场景

用户选择仓库及两个提交后，系统识别变更的代码实体，沿依赖关系查找潜在影响，并生成带源码定位和传播路径的报告。用户可以核对证据，对结论给出反馈。

## 建议首版需求

| 编号 | 能力 | 建议验收条件 |
| --- | --- | --- |
| FR-01 | 仓库与版本选择 | 能读取授权的本地 Git 仓库；把用户输入的引用解析并保存为明确提交 SHA；不可访问或不存在的提交返回清晰错误 |
| FR-02 | 代码解析 | 对选定语言提取约定的实体与关系；列出成功、失败和不支持的文件；不把失败文件作为已完整分析 |
| FR-03 | 图谱构建 | 实体与关系包含仓库、提交版本及来源定位；不同提交的数据不会混为同一快照 |
| FR-04 | 变更识别 | 识别新增、修改与删除的文件和实体；重命名或实体匹配不确定时保留状态；定位失败时降级到文件级结果 |
| FR-05 | 影响分析 | 输出直接与间接潜在影响、传播路径和分析边界；支持循环检测及遍历范围限制；能说明哪些关系未解析 |
| FR-06 | LLM 解释 | 使用分析证据生成解释，引用可校验的证据标识；无证据的判断标注为推测；模型失败时仍可查看基础分析 |
| FR-07 | 报告展示与导出 | 报告包含分析版本、变更摘要、影响清单、证据及局限；导出形式待确认；源码定位包含所属提交 |
| FR-08 | 任务状态 | 展示排队、运行、完成、部分完成、失败状态；保留失败原因；失败或部分结果不显示为完整分析成功 |

## 可在核心流程后补充

- FR-09：将已有测试与受影响实体关联，区分“仓库中存在的测试”与“模型建议新增的测试”。
- FR-10：记录用户对误报、遗漏和解释质量的反馈，用于离线评估。
- FR-11：支持 PR 接入、增量索引和历史报告比较，是否进入首版待评审。

## 非功能要求草案

| 方面 | 要求方向 | 仍需确定 |
| --- | --- | --- |
| 可追溯 | 记录提交 SHA、解析配置、图谱版本、模型标识、提示模板版本及证据引用 | 日志与结果保存周期 |
| 数据处理 | 源码访问限于授权范围；凭据不进入日志或报告；外部模型调用遵循项目确认的数据边界 | 部署环境和源码外发约束 |
| 可靠性 | 解析和模型调用失败可诊断；基础分析与模型解释分别报告状态 | 重试、取消和超时策略 |
| 性能 | 分别测量解析、构图、查询、模型调用耗时及资源用量 | 仓库规模与时间阈值 |
| 成本 | 记录模型用量、单任务费用估算和存储开销 | 预算上限 |
| 可维护性 | 解析器、图存储与模型调用之间保留清晰接口 | 最终技术栈及接口形式 |

## 首版验收样例

至少准备以下有人工预期结果的小型代码样例：

1. 修改被多个函数调用的公共函数，核对直接与间接调用方。
2. 修改接口或函数签名，核对相关引用与证据。
3. 删除函数，验证基准版本中的调用关系仍参与分析。
4. 新增函数及调用方，验证目标版本中的关系参与分析。
5. 出现循环调用、重命名和解析失败，验证不会无限遍历或隐藏分析缺口。
6. 模型调用超时或输出无效引用，验证基础结果可用且异常明确展示。
7. 两个提交内容相同，验证生成无变更报告。

每个样例保存代码版本、预期实体、预期路径、实际结果与差异。精确率、召回率等指标使用明确的人工标注范围，不能仅用报告是否生成衡量效果。
