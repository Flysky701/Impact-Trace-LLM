# 需求规格 v0.2（评审稿）

状态：课程约束、双角色方案、基础结构浏览与 AI 修改记录已确认；具体实现和验收细节仍为草案。本文不代表功能已经实现。

更新时间：2026-11-06。保留原 F1～F10 与 FR 编号；本次补充功能优先级、扩展边界及验收条件。核心业务细节仍按评审稿管理，扩展功能属于后续候选，不计入首版必做数量。实际完成情况见[项目现状](project-status.md)，顺序见[阶段计划](roadmap.md)，页面安排见[产品设计](product-design.md)。

## 核心场景

用户从仓库进入，选择两个提交或后续接入的 PR，先查看变更文件，再对照修改前后的函数流程与模块关系；旧图标红改动位置，点击追溯源码，并结合测试证据完成审阅。单版本结构浏览与 AI 修改记录保留；产品方向扩展为团队可用的 Git 代码审阅工作台。

交付约束已确认：课程项目，一个月以内完成，包含 8～10 个核心功能、至少两类角色、Web 系统和测试覆盖率 ≥75%。首版保留基础结构浏览与手动 AI 修改记录；自动修改代码与自动捕获其他 AI 工具的完整过程暂不列为首版要求。

## 已确认的角色与首版功能组织

开发者管理项目和仓库、选择版本并发起分析；审核者／测试负责人确认风险、添加审核意见、手动记录测试结果；两者均可查看图谱、报告与历史记录。角色属于系统权限，不等同于开发团队分工。首版实现必要权限，成员邀请和自定义角色后置。

按 10 个用户功能组织首版，下文 FR 编号是功能内部的能力拆分，不按条数重复计算核心功能：

| 功能 | 内容与对应需求 |
| --- | --- |
| F1 用户登录与权限 | 两类角色及必要的操作权限（FR-14） |
| F2 项目管理 | 创建、查看项目，维护基础信息（FR-15） |
| F3 仓库与版本管理 | 接入仓库并选择明确提交与比较方式（FR-01、FR-20） |
| F4 代码解析与图谱构建 | 提取实体、关系、有限控制流并保存版本快照（FR-02、FR-03、FR-18） |
| F5 修改任务与差异分析 | 手动任务记录、前后版本关联及差异定位（FR-04、FR-13） |
| F6 影响范围分析 | 直接和间接影响、传播路径（FR-05） |
| F7 结构与影响可视化 | 前后流程对照、旧图标红、分层架构与源码定位（FR-12、FR-07、FR-18、FR-19） |
| F8 LLM 解释报告 | 基于证据的结构说明与变更解释（FR-06、FR-07） |

此表是已确认范围的功能组织方案，详细验收仍需收敛。结构浏览先覆盖主要模块关系与源码定位；AI 修改记录先支持任务文字、前后提交和可选原始记录。

当前实施采用 Python/TinyDB 作为首批分析范围，前后端分别统计行覆盖率 ≥75%。页面、默认限制与实施顺序见[实施方案](implementation-plan.md)，具体测试矩阵见[测试方案](testing-plan.md)。

## 建议首版需求

| 编号 | 能力 | 建议验收条件 |
| --- | --- | --- |
| FR-01 | 仓库与版本选择 | 能读取授权的本地 Git 仓库；把用户输入的引用解析并保存为明确提交 SHA；不可访问或不存在的提交返回清晰错误 |
| FR-02 | 代码解析 | 对选定语言提取约定的实体与关系；列出成功、失败和不支持的文件；不把失败文件作为已完整分析 |
| FR-03 | 图谱构建 | 实体与关系包含仓库、提交版本及来源定位；不同提交的数据不会混为同一快照 |
| FR-04 | 变更识别 | 识别新增、修改与删除的文件和实体；重命名或实体匹配不确定时保留状态；定位失败时降级到文件级结果 |
| FR-05 | 影响分析 | 输出直接与间接潜在影响、传播路径和分析边界；支持循环检测及遍历范围限制；能说明哪些关系未解析 |
| FR-06 | LLM 解释 | 使用分析证据生成解释，引用可校验的证据标识；无证据的判断标注为推测；模型失败时仍可查看基础分析 |
| FR-07 | 报告展示与导出 | 报告包含分析版本、变更摘要、影响清单、证据及局限；导出形式待确认；源码定位包含所属提交 |
| FR-08 | 任务状态 | 展示排队、运行、完成、部分完成、失败状态；保留失败原因；失败或部分结果不显示为完整分析成功 |
| FR-12 | 项目结构理解 | 无需提供变更即可浏览单版本的文件或模块关系；查看简短职责说明并定位依据；区分代码直接提取的结构与模型推测的职责 |
| FR-13 | AI 修改记录 | 将用户任务描述、前后提交及实际差异关联展示；允许人工附加已有操作记录；标明记录来源和缺失阶段，不把模型事后解释当作原始过程记录 |
| FR-14 | 登录与角色权限 | 能分别使用开发者和审核者账号登录；服务端校验写操作权限，两类角色均可查看图谱和报告 |
| FR-15 | 项目管理 | 开发者能创建项目、维护基础信息并关联仓库；审核者能查看可访问项目 |
| FR-16 | 风险审核与测试记录 | 审核者能确认风险、添加意见、手动填写测试状态与结果；记录操作者、时间及所属分析任务 |
| FR-17 | 历史分析记录 | 两类角色均可查看可访问项目的历史任务、版本、结果和审核记录；无需重新调用模型即可查看已有报告 |

编号沿用已有草案，新增需求不改变原编号。FR-07 首版以页面报告为主，文件导出可后置；FR-08 只需适配实际执行方式，没有队列时无需实现排队系统。

## 建议的演示界面

2026-11-06 用户将前后流程对照、旧图标红和自动架构图确定为主要方向，要求仓库式交互与自然视觉引导。比较页以流程变化为默认主视图；整体模块架构仍可从“架构”独立进入，结构树与影响清单作为补充，避免单张图承载全部内容。详见[产品设计 v0.3](product-design.md)与[新版原型](prototype/review.html)。

导航采用“代码 / 架构 / 比较 / 检查 / 审阅记录”。仓库、固定 SHA 与比较方式始终可见；左侧文件列表、中间主图、右侧源码依据构成审阅工作区。问答在选中代码的详情中折叠展示，指标进入检查页。标题和按钮直接说明对象与动作，不添加宣传性修饰。

## Git 审阅与图形差异需求

| 编号 | 能力与优先级 | 验收边界 |
| --- | --- | --- |
| FR-18 | 前后流程对照与旧图标红 · 核心 | 两图分别绑定实际比较的 SHA；修改与删除位置在旧图标红，新增位置仅作对比注释；新图显示新增/修改；边的条件、方向和端点也参与比较；可切原始图与 diff；无可靠节点匹配时标待确认 |
| FR-19 | 分层自动架构图 · 核心的模块/调用图，其他图种后续 | 一个视图一个抽象层；箭头有明确语义；默认小范围、可展开且保留完整结构入口；每个节点/边有证据或明确推断标记；不将目录图称为部署图，不将调用图称为运行顺序 |
| FR-20 | 仓库式版本与比较语义 · 核心；PR 接入后续 | 分支/标签解析为 SHA；直接比较使用 base/head，PR 模式保存 base tip/head/merge-base，旧图与 diff 使用同一实际基准；旧报告不随分支移动改变 |
| FR-21 | 检查指标与覆盖率导入 · 优先增强 | 数值绑定仓库、SHA、报告来源和范围；覆盖率区分行/分支/变更可执行行；未导入、不适用、版本不匹配分别显示；缺失部分标记不完整；平台覆盖率不得冒充样例仓库覆盖率 |
| FR-22 | 上下文代码问答 · 辅助增强 | 继承当前仓库、SHA、实体与比较范围；回答引用证据，无证据说明不足；不自动执行测试或修改代码；界面默认折叠 |
| FR-23 | 分层活动图 · 新增核心图种（F4/F5/F7/F8） | 先选场景，再看整体行为 → 模块活动 → 子活动/函数 → 代码；两版对照与旧图标红共用比较版本；父级显示“含改动”，子级定位实际变化；Agent 归纳有证据和来源，不将推断顺序作为确定路径 |
| FR-24 | 数据库与数据模型图 · 优先增强（F4/F7） | 有 schema/ORM 时提取表、字段、主外键与约束；文档型仓库展示有依据的逻辑结构；缺信息显示未知；后续两版结构差异绑定各自 SHA，支持关联读写活动，不虚构外键或变更 |

FR-18 首版只承诺所声明的 Python 控制流语法与函数范围，复杂语法折叠并提示，不能用模型编造完整业务执行链。先完成一条真实可核对的比较流程，再扩大函数与图种范围。

FR-23 是独立的图种，不将现有函数流程图更名为活动图。仓库可能有多个场景，场景目录需标明覆盖入口与缺口；首版先实现固定更新场景的逐层阅读。红色父活动汇总子级代码变化，不能直接等同于业务风险。FR-24 的原型先用 TinyDB 实际逻辑存储结构，关系型 ER 提取另设带 schema 的样例验收。

## 功能扩展规划

P0 为 F1～F10 的课程可用版，优先打通 FR-18～FR-20 的有限范围；P1 为核心流程后的优先增强；P2 按实际需求启动。下列 E 编号用于安排扩展，不改变已有 FR 编号。工作量“低 / 中 / 高”是相对于已有核心流程的估计，不是工期承诺。

| 编号与优先级 | 用户价值与最小功能 | 依赖与工作量 | 可验收结果 |
| --- | --- | --- | --- |
| E1 · P1 测试关联（FR-09） | 审核者将影响候选关联到已有测试，形成回归检查清单；同时展示建议新增的测试 | F6/F9；中 | 已有测试能定位到指定 SHA 的文件与定义；保存人工/静态引用等来源；未运行显示“未执行”；模型建议不会混为已有测试 |
| E2 · P1 报告导出（FR-07） | 导出 Markdown 与 JSON，便于课程报告和离线复核 | F8/F9/F10；低 | 导出含两个 SHA、改动、影响路径、证据、诊断和截至导出时的审核记录；结果与页面一致；导出不请求模型，不包含凭据或本机绝对仓库路径 |
| E3 · P1 误报与遗漏反馈（FR-10） | 用户对影响候选标记“需关注 / 不相关 / 待确认”，补充原因；遗漏项另附源码依据 | F6/F9/F10；低至中 | 记录操作者、任务、候选与时间；原始分析结果保留；人工补充不伪装成算法发现；无标注分母时不显示准确率 |
| E4 · P1 历史报告比较（FR-11） | 比较同项目两次分析的候选与审核变化，帮助跟踪一次修改的后续处理 | 稳定任务存储与实体匹配；中 | 并列展示两组 SHA 及分析配置；新增/消失候选可追溯；配置不同明显提示；不能确定对应关系的实体单列，“消失”不自动等同于问题修复 |
| E5 · P1 代码问答（FR-22） | 针对选中代码回答“这一步做什么”“为什么影响这里”；默认折叠，排在流程与检查后 | F4/F6/F8；中 | 回答引用当前范围的证据，能打开对应源码；资料不足明确说明；切换快照后不混用旧证据；用量计入任务或会话，不生成无依据的确定调用关系 |
| E6 · P2 第二语言 | 首选 TypeScript/JavaScript 作为第二种语言候选，复用图谱、报告和审核页面 | Python 流程稳定、统一解析输出、第二语言样例；高 | 固定样例完成实体、导入与声明支持的调用解析；输出能力清单与未解析诊断；不把支持两种语法称为支持跨语言调用链 |
| E7 · P1 PR 只读接入（FR-11、FR-20） | 团队试用前接入单个 PR，沿用现有比较和审阅流程 | 本地两版本分析稳定、托管平台接入配置；中至高 | 保存 base tip/head/merge-base SHA，实际差异与旧图基准一致；PR 更新不改变旧报告；不自动评论、改码或合并 |
| E8 · P2 快照复用与增量分析（FR-11） | 重复分析先复用相同快照；有性能需要时再只重算受影响部分 | 快照标识、解析配置与规则版本稳定；先复用为中，增量为高 | 同仓库、SHA、解析器版本、配置一致才复用；配置变化触发失效；引入增量后在固定样例中与完整解析结果一致 |

补充 E9 · P1 检查指标与覆盖率导入（FR-21）：先导入一种带提交信息的已有覆盖率报告，计算变更可执行行的覆盖情况并定位未覆盖行。绑定报告来源、范围与采集时间；与人工测试记录分开。工作量中，依赖版本差异与源码定位，不依赖模型。

先完成流程对照与架构阅读，再优先 E1/E9 检查证据与 E2 导出。团队试用需要 GitHub 工作流时接入 E7；E5 作为上下文辅助随后接入，E3/E4 随报告积累补充；第二语言与增量后置。E5 初期复用已有实体、路径和证据，无需先建设完整 Wiki 或向量检索系统。

### 首版预留的扩展边界

在实现相关核心模块时保留以下约定，不单独建设插件平台：

| 边界 | 首版需要保留的约定 | 支撑的扩展 |
| --- | --- | --- |
| 解析结果 | 统一输出实体、关系、源码范围和诊断；实体绑定快照；解析器声明语言和支持的关系类型 | 第二语言、代码问答、测试关联 |
| 版本与证据 | 快照标识包括仓库、SHA、解析器版本和配置；证据绑定快照、路径、行范围；跨版本实体匹配单独记录 | 历史比较、快照复用、可核对导出 |
| 分析任务 | 保存输入、配置、规则版本和独立的静态/模型状态；结果固定；重试引用原任务 | 历史比较、模型替换、失败恢复 |
| 模型适配 | 只接收筛选后的证据，返回解释与证据 ID、用量和错误；调用方不依赖某一厂商响应格式 | 第二模型、代码问答 |
| 审核与反馈 | 追加记录引用任务/候选 ID，保存操作者与时间；人工结论与算法结果分离 | 测试关联、误报反馈、审核历史 |
| 报告读取 | 页面和导出读取同一份已保存结果；接口响应保留格式版本 | 导出、PR 入口及后续外部集成 |

这些约定在现有应用和 SQLite 内实现。只有实际规模或部署需求证明不足时，再考虑独立图数据库、任务队列或服务拆分。

### 暂不安排的功能

自动编写或合并代码、自动执行被分析仓库测试、跨仓库完整调用链、跨语言语义推导、自定义角色体系及大型管理看板不进入近期计划。现有人工测试记录继续明确标注“平台未执行”，风险排序不使用未经校准的发生概率。

## 首版验收样例

必做演示与基本检查：

1. 导入选定开源项目，在结构图中找到主要模块，并从解释跳转到源码。
2. 记录一次 AI 修改任务，对比两个提交，验证至少一条直接依赖和一条间接影响路径。
3. 演示新增或删除实体中的一种变更，验证使用了正确版本的关系。
4. 模型不可用或输入版本无效时显示清晰提示；模型不可用时仍可查看基础结果。
5. 使用开发者账号发起分析，再使用审核者账号确认风险、填写意见和测试结果；检查越权写操作被拒绝，历史报告能保留审核记录。
6. 运行平台的自动化测试，保存覆盖率报告，按项目测试方案明确的统计口径验证 ≥75%。课程未规定更细口径。此指标针对平台测试，与审核者手动记录样例仓库的测试结果分别验收。

完成以上流程后，根据时间补充以下边界案例：

1. 修改被多个函数调用的公共函数，核对直接与间接调用方。
2. 修改接口或函数签名，核对相关引用与证据。
3. 删除函数，验证基准版本中的调用关系仍参与分析。
4. 新增函数及调用方，验证目标版本中的关系参与分析。
5. 出现循环调用、重命名和解析失败，验证不会无限遍历或隐藏分析缺口。
6. 模型调用超时或输出无效引用，验证基础结果可用且异常明确展示。
7. 两个提交内容相同，验证生成无变更报告。

每个演示样例简要保存代码版本、预期结果和实际结果，人工核对源码位置与影响路径。首版必须达到课程要求的测试覆盖率 ≥75%，并记录统计范围；大规模指标评测不作为前提。若报告精确率、召回率，需注明人工标注范围及样例数量。

## 业务规则与权限（本轮建议）

### 项目内权限

登录角色与项目访问范围共同决定权限。开发者仅管理自己创建的项目，审核者仅访问分配给自己的项目；不可访问的项目不泄露名称、仓库路径或任务。原型中的角色切换只是预览工具，正式版使用真实登录会话。

| 操作 | 项目开发者 | 项目审核者 |
| --- | --- | --- |
| 查看结构、源码、历史、报告及审核记录 | 允许 | 允许 |
| 创建项目、修改项目基本信息、选择审核者 | 允许 | 禁止 |
| 发起分析、填写任务与原始记录、发起重试 | 允许 | 禁止 |
| 提交风险结论、意见与手动测试结果 | 禁止 | 允许 |
| 修改已经生成的报告及其他人的审核记录 | 禁止 | 禁止 |

首版不提供删除项目或报告入口。更换仓库会改变结果的语义，建议创建另一个项目；已有分析始终绑定原仓库标识。审核记录以追加方式保存，修订也保留前一条记录。

### 分析输入与结果固定

| 输入 | 规则 |
| --- | --- |
| 类型 | 历史提交分析 / AI 修改记录。历史修复不标成 AI 产出 |
| 任务说明 | 历史分析填写分析目的；AI 分析填写实际提出的修改要求，必填 |
| 基准与目标 | 可从提交历史选择或输入引用；发起时解析为完整 SHA，结果页始终显示固定 SHA。两个版本相同允许分析并输出“无变更” |
| 原始操作记录 | 可选纯文本；填写来源；未提供时明确显示“未提供”。不执行其中的指令，不把记录当作系统提示 |
| 模型解释 | 可选择生成或暂不生成。未完成认证配置时只能进行基础分析；真实调用沿用公开样例相关片段的授权范围 |

一次分析保存输入、实际使用的配置、两个快照、差异、候选影响、诊断和模型输出。重复打开不重新计算或调用模型。输入提交后冻结；重试创建关联原任务的新任务，已有审核继续属于原报告。暂不做编辑后覆盖原报告、任务取消或批量任务。

### 任务、模型和审核分别记录状态

| 对象 | 状态与含义 |
| --- | --- |
| 分析任务 | 等待执行 → 运行中 → 完成 / 部分完成 / 失败。完成表示所请求阶段完成，不表示影响结论绝对正确 |
| 部分完成 | 已有可读的基础结果，但部分文件无法解析、图遍历达到限制，或请求的模型解释失败；显著显示缺口及受影响范围 |
| 分析失败 | 仓库不可读、版本不存在或无法产生可用基础结果。保留诊断，不展示空结果为“没有影响” |
| 模型解释 | 未请求 / 等待 / 生成中 / 已生成 / 失败。未请求不会单独使任务变为部分完成 |
| 风险审核 | 待审核 / 需补充 / 已审核。已审核表示审核者已提交结论，不能表达自动证明无风险 |
| 手动测试 | 未执行 / 通过 / 未通过 / 受阻。与审核结论独立保存；未执行也可提交审核，但须说明原因 |

首次提交需要结论和非空审核意见。记录测试“通过”或“未通过”时须说明检查对象、实际命令或手动步骤，以及结果摘要；“受阻”须说明原因。测试结果是用户填写，界面标注“手动记录，平台未执行”。审核时间和身份由服务端产生。

### 影响与证据表达

- “改动的实体”和“可能受影响的实体”分别统计，同一实体可同时属于两者，不直接相加当作总量。
- 图中的控制流、调用方向与影响传播方向分别提供图例；比较页默认前后流程，影响视图使用反向传播方向，例如 `update → upsert` 表示 upsert 可能受 update 改动影响。
- 每个候选影响提供起点、终点、路径、关系类型、所属版本及来源位置。删除实体优先查基准快照，新增实体查目标快照；不能跨版本拼接一条未说明的路径。
- 静态提取事实、解析候选、模型推测、人工确认分开标识。没有可解释路径时不伪造确定关系。
- 风险优先用“需核对的问题 + 依据 + 建议检查”，首版不加入未经校准的分数或高风险百分比。
- 全貌视图显示分析范围、粒度与解析缺口；图中省略的定义能在结构树查看。模块导入级影响与函数调用级影响分别标识，未标记的实体不能称为“确定无影响”。无变更时保留结构视图，但不添加影响标记。
- 已有测试须能在指定版本找到；模型建议新增的测试单独显示，不声称已存在或已经通过。
