## 产品主线

面向团队中的开发者和代码审核者，围绕一次具体变更回答三个问题：原来的逻辑如何工作，修改后怎样工作，需要检查哪些调用方和测试。

使用顺序为：仓库 → 选择基准与目标 → 文件差异 → 前后流程对照 → 架构与调用上下文 → 检查证据 → 审阅记录。单版本浏览仍可独立使用，帮助新成员理解代码。代码问答放在所选模块、函数或变更旁边，避免用户提问前还要重述仓库和版本。

“面向公司”先落实为一个团队能实际完成代码审阅：版本准确、证据可查、权限生效、结果可回看。当前没有完成私有仓库接入、企业身份认证、托管部署或企业级可靠性验证，不将产品定位等同于这些能力已具备。现有公开样例的源码外发约定不自动扩展到公司的私有代码。

## 功能主次

| 层级 | 内容 | 本期取舍 |
| --- | --- | --- |
| 核心 | Git 版本比较、前后流程图、旧图变化标红、模块依赖与调用上下文、源码证据、审阅记录 | 第一条完整流程围绕这些能力实现 |
| 审阅辅助 | 变更文件数、解析缺口、已有测试线索、覆盖率报告导入、报告导出 | 有证据才显示数值；先用已有报告，不自动运行仓库测试 |
| 理解辅助 | 围绕所选代码的问答、简短模块说明、历史比较 | 共用版本与证据，折叠在详情中，避免成为第二套主工作台 |

## 仓库信息架构

顶部固定仓库名，主导航为“代码 / 架构 / 比较 / 检查 / 审阅记录”。进入比较后保持仓库、比较模式、基准与目标 SHA 可见；切换视图不改变分析范围。正式版的分支与标签选择器最终解析为固定 SHA，不能随分支移动而改写历史结果。

| 页面 | 默认内容 | 次要操作 |
| --- | --- | --- |
| 代码 | 分支或固定提交、目录树、文件源码、提交记录 | 从函数进入流程或调用上下文 |
| 架构 | 当前版本的模块依赖；进入模块后展开局部调用关系 | 返回上层、查看未解析项、切换图种 |
| 比较 | 左侧变更文件，中间前后流程，右侧源码依据 | 旧图标注、原始旧图、代码差异、查看影响调用方 |
| 检查 | 当前比较的变更规模、解析诊断、测试报告与覆盖率 | 定位未覆盖的变更行或缺失报告 |
| 审阅记录 | 同一固定比较的意见与手动测试记录 | 追加结论，回看之前的意见 |

分析任务成为比较操作的后台记录，用户不必先理解“任务平台”才能开始审阅。本地 Git 先支持；GitHub 的 PR 入口后续映射到相同比较记录，不复制一套分析逻辑。

### 比较方式

- 两个提交直接比较：旧图属于 base SHA，新图属于 head SHA，代码差异也是这两个版本之间的差异。
- PR 比较：保存 base tip、head tip 和 merge-base；实际旧图和 diff 使用 merge-base，新图使用 head，并在页面写明。不能把 base tip 的图与 merge-base 的差异混用。
- 历史结果冻结上述版本与比较方式，分支名称只作来源说明。原型案例 B 的基准是目标的父提交，当前只演示直接比较。

比较语义依据 [GitHub 的两点与三点比较说明](https://docs.github.com/en/pull-requests/reference/branches)。

## 流程图变更

### 三种阅读方式

1. **前后对照**：左侧旧流程，右侧新流程；匹配步骤保持相对位置与相同缩放基准。新增节点使用预留空间，避免整张图重排后难以比较。
2. **旧图标注**：保留旧版拓扑，将被修改的步骤标红；删除步骤使用红色虚线与“删除”标签。新插入的步骤在旧图旁以虚线注释标记插入位置，不能画成旧版真实节点。
3. **原始旧图与代码差异**：能关闭标记查看原图，也能切回逐行 diff。每个变化都可以定位两侧源码；无法匹配的节点显示“待确认对应关系”。

| 语义 | 展示 |
| --- | --- |
| 旧版修改位置 | 红色边框与“修改”标签 |
| 旧版删除节点或边 | 红色虚线与“删除”标签 |
| 新版新增节点或边 | 绿色与“新增”标签 |
| 新版修改节点或边 | 琥珀色与“修改”标签 |
| 未变更上下文 | 中性灰色，默认保留 |
| 潜在影响 | 单独的影响标记与可切换传播路径，避免与真实差异混淆 |

颜色同时配合文字和线型；红色不代表“已发生故障”。选择状态不能覆盖变更语义。关系端点、条件或方向发生变化时，边也参与比较，不只比较节点文本。

### 流程图与调用图分别处理

调用图描述“谁调用谁”，不能说明调用先后、条件和循环。流程图描述所选函数内的步骤、分支、循环、提前返回和可识别的异常路径。首版基于 Python AST 构建有限的函数控制流，再将调用步骤关联到调用图。

首批支持普通语句块、if/else、for/while、break/continue、return 和显式 raise；try/except/finally、生成器、异步与动态行为可以先保留带源码的折叠节点，注明内部未展开。未支持的语法不能被静默连成一条确定路径。业务级流程摘要可以由模型辅助命名，但模型不能自由增删确定的控制流边；摘要始终标明来源和范围。

节点匹配先使用两版实体映射、语法结构、源范围及邻接上下文，不用显示文案或行号充当稳定 ID。代码移动、重命名、提取函数等歧义保留为待核对；无可靠匹配时显示并列子图，不强行宣称对应。

### 原型示例

采用 TinyDB 案例 B 的 `Table.update(doc_ids=...)`：旧版从全部请求 ID 直接逐个更新，新版先过滤当前表中存在的 ID，再执行更新并返回实际更新的 ID。旧图标红的是输入收集与更新步骤，新增过滤在旧图上只是对比注释。

原型的图由源码人工整理，展示 doc_ids 分支摘要，未展开用户回调、其他条件分支和存储内部逻辑。真实 Git diff 与两版源码摘录来自本地固定提交；图不是正式自动分析的结果。此例主要展示修改和插入，正式实现还需用小型固定样例检查删除、重命名、循环和异常分支。

## 自动生成哪些架构图

| 图种 | 回答的问题 | 生成依据 | 优先级与限制 |
| --- | --- | --- | --- |
| 模块依赖图 | 项目由哪些模块组成，谁依赖谁 | 文件/模块、导入语句、解析证据 | 核心；同层只放模块，按需展开 |
| 局部调用图 | 谁调用当前函数，它又调用谁 | 有来源的调用边与未解析诊断 | 核心；先明确调用，动态目标标未知 |
| 函数流程图 | 执行步骤和分支怎样变化 | 两版控制流、实体与节点映射 | 核心；按函数和分支收敛范围 |
| 活动图 | 整体场景与模块完成什么行为，行为怎样衔接 | 入口、调用/控制流、数据读写与 Agent 归纳，活动关联源码证据 | 核心新增图种；场景 → 模块 → 子活动逐层展开，可转入函数流程 |
| 系统概览与组件图 | 服务、存储和模块的职责与边界 | 入口、配置、路由、持久化及部署文件 | 后续；按 C4 分层，事实与推断分开；库项目不强行画服务部署图 |
| 时序图 | 一条具体入口沿哪些组件交互 | 已解析调用链或导入的运行轨迹 | 后续；静态候选序列不冒充真实运行顺序 |
| 数据模型图 | 表、字段或文档结构如何关联 | ORM 定义、迁移、schema 或明确的存储结构 | 优先增强；关系型项目显示 ER，文档型项目显示逻辑模型；不虚构外键 |

可读性规则：每张图只回答一个问题；默认约 5～9 个主要节点，超出时分组或钻取，而非缩小字体；箭头写明导入、调用、读写或条件；保持流向一致；局部展开后保留面包屑。完整定义仍在目录/结构树中，不因默认图折叠而丢失。每张图显示提交、范围、证据类型与省略内容。

图的内部数据与布局、显示文字分离。首版继续评估既定交互图组件；Mermaid 适合文档导出，不要求承担全部交互和布局稳定性。借鉴开源 skills 的设计方法，不将它们当作可直接替代分析器的运行库。

## 活动图的分层审阅

比较页增加“图种：函数流程图 / 活动图”。活动图描述行为 A → 行为 B，不以函数名或目录列表代替行为。一个项目通常有多个入口和场景：先展示场景目录，再为选定场景生成整体活动图；不存在能够覆盖任意仓库所有行为的一条固定直线。

| 层级 | 用户看到的内容 | 标红与展开 |
| --- | --- | --- |
| 整体场景 | 如提交更新请求 → 更新文档 → 接收结果，节点标注责任模块 | 含改动的模块活动标红，点击进入模块；保留未改活动作为上下文 |
| 模块活动 | 如准备 ID → 读取表数据 → 修改文档 → 写回 → 清理缓存与返回 | 只标红涉及改动的子活动，继续展开或定位函数 |
| 函数与代码 | 既有前后函数流程、条件/循环、实际 diff | 精确到步骤、边及两版源码行 |

父活动的“含改动”来自子级变化的汇总，不能解释为整个模块都被重写。下钻后保留面包屑、两版 SHA、选择状态与变更语义。无源码修改但可能受影响的活动使用独立标记；仅注释/格式变化与控制流变化分别记录，不能自动声称业务行为改变。红色摘要不向所有后续活动无差别扩散。

Agent 可以读取仓库，识别入口、归纳行为名称、划分责任模块并提出活动层级。输出应为结构化活动记录：活动 ID、父活动、场景、责任模块、关联实体与两侧证据、前驱/后继、条件及归纳来源。静态提取与引用校验核对版本、调用点和控制结构，界面区分确定关系、Agent 推断及人工确认。条件、并发和异常只有证据充分时才画出；不确定顺序不画成确定的 A → B。

两版活动应通过关联代码和父子上下文匹配，不能仅根据 Agent 改写后的标题判断增删。数据模型使用同一版本与证据体系，后续可对照表/字段/约束变化，并关联到读写这些数据的活动；“字段变化影响业务”的结论仍需路径依据。

v0.4 原型新增 TinyDB“文档更新场景”的活动对照、父级含改动标红、模块展开、转入函数流程，以及架构页的数据模型入口。数据模型为数据库映射 → 命名表 → 文档内容的逻辑结构，未展示 SQL 外键或数据库结构差异。活动是固定源码的人工摘要，仅展示正常完成路径；自动 Agent 归纳和通用多场景生成尚未实现。

## 指标与问答的边界

检查页围绕当前比较展示指标，避免占用流程图的主要空间：

| 指标 | 数据与口径 |
| --- | --- |
| 变更文件与实体 | Git diff 与实体映射；改动实体、影响候选分别统计，不相加重复计数 |
| 解析完整性 | 成功解析文件数 / 纳入范围的文件数，同时列出失败、跳过及不支持项；不称为语义解析准确率 |
| 变更行覆盖率 | 目标版本中已执行的新增/修改可执行行数 / 有有效报告数据的新增/修改可执行行数；有未报告的变更文件时标记“部分数据”并列出缺口 |
| 行覆盖率与分支覆盖率 | 从同仓库、同 SHA 的报告分别导入；两者不能混算 |
| 测试与审阅状态 | CI 导入或人工记录，并标明来源、时间和执行范围；未执行不显示通过 |

没有报告显示“未导入”；没有可执行变更行显示“不适用”；报告提交不一致显示“版本不匹配”，不可参与覆盖率对比。报告缺少范围说明时不把未知行当作已覆盖或未覆盖。数值比较必须有一致的范围和采集口径；不生成一个模糊的综合质量分。

先支持一种覆盖率格式，例如 Coverage.py JSON，并保存来源、提交、采集时间、路径归一化规则及排除范围；随后按需要补充其他格式和 CI 读取。被分析仓库的覆盖率，与 ImpactTrace 平台自身 ≥75% 的课程门槛分别管理。[Coverage.py 文档](https://coverage.readthedocs.io/en/7.14.1/branch.html)说明行与分支信息可以分别获得。

问答继承当前仓库、SHA、所选函数或比较范围，回答引用现有证据。默认折叠；先提供“为什么影响这里”“这一步做什么”等上下文问题。不能把事后模型解释当作原始 AI 操作记录，也不凭问答结果宣布测试通过。

## 页面表达

页面用“仓库名、路径、版本、动作”组织层级，保留代码仓库的熟悉感。标题直接描述变更；按钮使用“比较、查看源码、提交审阅”，不添加口号、装饰性英文栏目或宣传文案。

视觉焦点依次为变更标题与版本、中央流程对照、选中节点、右侧证据。默认不放大面积指标卡、重复摘要、彩色装饰图标或聊天欢迎区。常规布局使用留白、分隔线和中性背景；颜色主要编码变化和状态。

桌面采用文件列表 / 主图 / 证据三栏。中等宽度将证据放到图下方；窄屏按旧图、新图顺序堆叠，图内可滚动，不能通过缩小全部文字勉强并排。按钮有文字，图节点可以键盘选中，选中后两侧对应节点与证据同步。

## 原型范围与后续验证

新版原型支持仓库导航、三个流程阅读方式、真实代码差异、固定源码定位、模块逐层浏览、局部调用图、检查页、上下文问答示例和内存审阅记录。角色预览不等同于后端权限；图形是固定案例，问答是人工示例，覆盖率尚未导入。

2026-11-06 已完成原型的定向 DOM 交互检查：前后/旧图/原图/diff 切换、节点证据、模块展开、调用图返回流程、检查空状态、源码、审核文本安全显示及上下文回答。后续已解决本机预览连接问题，在浏览器中查看前后流程、旧图标红及模块/调用图。此检查不计入正式应用覆盖率。

v0.4 已检查活动图的父级与子级标红、原图/旧图/diff 切换、面包屑返回、转入函数流程及数据模型入口；并在当前浏览器侧栏宽度下核验整体活动、模块活动与数据模型的实际画面。未重新统计正式应用覆盖率，其他屏幕宽度仍待需要时检查。

正式实现按[阶段计划](roadmap.md)推进。验证重点是版本匹配、节点/边变更、图文证据一致性、缺失数据状态和真正的审阅流程，而不是图种数量或装饰效果。
