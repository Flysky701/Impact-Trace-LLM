## 首个真实分析案例

以[样例验证中的案例 B](sample-validation.md)为第一条贯通流程：

1. 保存基准 `8a2dc204c265c07ce8506a3599a28e720b6dcdd7` 与目标 `76d21d26c682e1ca6ca25bd8e81edf9f609ac52f`。
2. 对照 Git diff 标出 `Table.update`、`remove`、`upsert` 等实际变化；匹配不确定的实体保留状态。
3. 展示 `update → upsert` 的反向影响路径，并明确 upsert 本身也有改动，避免重复统计。
4. 从每条路径打开所属版本的源码，列出动态转发等未解析范围。
5. 对照 update 的 doc_ids 分支，展示旧版直接更新与新版先筛选再更新的区别；节点和边均能定位两版源码。
6. 保存基础报告，随后接入审核与模型解释。

该案例证明固定场景中的直接调用候选。两级函数传播、删除实体和循环另用小型固定样例验证，不能为满足演示要求在 TinyDB 中虚构路径。真实 AI 修改案例需有真实任务与前后提交，不把历史修复改名充当。

## 扩展时保留的基础

- 分析输入保存仓库标识、两个 SHA、解析器与规则版本、配置；历史报告固定，重试建立关联的新任务。
- 解析输出统一为实体、关系、证据位置和诊断，并声明语言能力；图谱界面不直接依赖 Python AST。
- 静态结果与模型解释分开保存；模型不可用不丢失基础报告。
- 审核和反馈引用任务及候选 ID，以追加记录保留历史，不能静默覆盖算法证据。
- 继续使用现有 FastAPI、Vue 与 SQLite。新增业务时再按职责拆分模块，不为预想扩展提前引入微服务、图数据库或队列集群。

首版不纳入自动改码、自动合并、自动运行被分析仓库测试、跨仓库/跨语言调用链、复杂组织权限及生产级运维平台。
